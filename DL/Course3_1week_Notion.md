

1주차는 모델 성능을 효율적으로 개선하기 위해 **목표를 명확히 설정하고, 평가 지표와 데이터셋을 어떻게 정의해야 하는지**를 다룹니다.

## 1. 직교화 (Orthogonalization)

머신러닝 프로젝트에서는 조정할 수 있는 하이퍼파라미터나 시도할 수 있는 전략이 매우 많습니다. **직교화**란 한 번에 하나의 기능(목표)만을 독립적으로 조정할 수 있도록 조절 장치(Knob)를 설계하는 개념입니다.

### 1).자동차와 TV의 비유

* **TV 조절 비유:** 화면의 가로 길이, 세로 길이, 기울기 등을 독립적으로 조절할 수 있는 버튼이 있다면 세팅이 쉽습니다. 하지만 버튼 하나가 가로와 세로, 기울기를 동시에 바꾼다면 원하는 화면을 만들기 매우 어렵습니다.
* **머신러닝에서의 4가지 독립적 단계 (Chain of Assumptions):**
1. **훈련 세트에 잘 맞추기 (Fit training set well):** 더 큰 네트워크 사용, Adam 등 최적화 알고리즘 변경
2. **검증 세트에 잘 맞추기 (Fit dev set well):** 정규화(Regularization), 더 많은 훈련 데이터 확보
3. **테스트 세트에 잘 맞추기 (Fit test set well):** 더 큰 검증(Dev) 세트 사용
4. **실제 환경에서 잘 작동하기 (Fit well in real world):** 검증/테스트 세트 변경, 평가 지표(Cost Function) 재설정



> **주의사항:** early stopping 같은 기법은 훈련 세트 오차와 검증 세트 오차에 동시에 영향을 미치므로 "덜 직교화된" 기법입니다. (그럼에도 자주 쓰이지만, 직교화 관점에서는 단일 목적 조정이 더 권장됩니다.)

## 2. 단일 숫자 평가 지표 (Single Number Evaluation Metric)

모델의 성능을 비교할 때, 여러 개의 평가 지표를 복합적으로 사용하는 것보다 **하나의 숫자로 측정되는 단일 지표**를 만드는 것이 개발 반복 속도를 대폭 향상시킵니다.

* **예시 (정밀도와 재현율):**
* Precision(정밀도)과 Recall(재현율) 두 가지 지표로 분류기 A, B를 비교하면 "Precision은 A가 높고, Recall은 B가 높은" 트레이드오프 상황에서 즉각적인 결정을 내리기 어렵습니다.


* **해결책 ($F_1$ Score 사용):**
* Precision과 Recall의 조화평균인 **$F_1$ Score**라는 단일 숫자를 정의하면, 모델 A와 B 중 어떤 것이 더 우수한지 즉시 판단하고 다음 실험을 진행할 수 있습니다.

## 3. 최적화 지표와 충족 지표 (Optimizing and Satisficing Metrics)

모든 성능 요구사항을 하나의 수식($F_1$ score처럼)으로 통합하기 어려울 때는 **최적화 지표(Optimizing Metric)** 1개와 **충족 지표(Satisficing Metric)** $N-1$개로 분류합니다.

* **최적화 지표 (Optimizing):** 극대화(또는 극소화)하고자 하는 핵심 지표 (1개만 지정)
* **충족 지표 (Satisficing):** 일정 기준(Threshold)만 만족하면 더 높아져도 상관없는 지표들

| 평가 항목 | 분류기 A | 분류기 B | 분류기 C | 선택 |
| --- | --- | --- | --- | --- |
| **정확도 (Optimizing)** | 90% | **92%** | 95% | **분류기 B** |
| **실행 시간 (Satisficing)** | 80ms | **95ms** | 1,500ms (기준 초과) | (기준: $\le 100\text{ms}$) |

* **실생활 예시 (음성 인식 AI 호출 - "Hey Siri"):**
* **Optimizing:** 호출어 감지 정확도 (가장 높을수록 좋음)
* **Satisficing:** 24시간 동안 발생하는 오작동(False Positive) 횟수 $\le 1$회 이하

## 4. 훈련 / 검증 / 테스트 세트의 분포 (Train / Dev / Test Distributions)

**Dev(검증) 세트와 Test(테스트) 세트는 반드시 동일한 분포(Same Distribution)에서 추출되어야 합니다.**

* **잘못된 사례:**
* Dev 세트: 미국, 유럽 등 특정 지역 사용자 데이터
* Test 세트: 아시아, 남미 사용자 데이터
* 결과: Dev 세트에 맞춰 모델을 열심히 최적화해도 Test 세트 성능이 떨어집니다.


* **올바른 접근:**
* 모든 지역/환경의 데이터를 하나로 섞은(Shuffle) 뒤 무작위로 Dev 세트와 Test 세트를 분할합니다.


* **지침:** Dev 세트와 Test 세트를 설정하는 것은 "과녁을 어디에 둘 것인가"를 결정하는 것입니다. 과녁 위치가 개발 도중에 흔들리지 않도록 미래에 실제 배치될 서비스 환경 데이터 분포를 반영해야 합니다.

## 5. 빅데이터 시대의 데이터셋 분할 비율과 크기

과거 머신러닝 교과서의 전통적인 데이터 분할 비율(60/20/20 또는 70/30)은 데이터 수가 적을 때 적합했습니다.

### 전통적 방식 (데이터 수 100~10,000개)

* Train / Dev / Test = **60% / 20% / 20%** 또는 **70% / 0% / 30%**

### 빅데이터 시대 (데이터 수 1,000,000개 이상)

* Dev 세트와 Test 세트는 모델을 평가 및 검증하기에 충분한 수(예: 10,000개)만 확보하면 됩니다.
* Train / Dev / Test = **98% / 1% / 1%** 또는 **99.5% / 0.25% / 0.25%**

### Test 세트가 꼭 필요한가?

* **Dev 세트:** 여러 알고리즘 중 최선의 알고리즘을 선택하기 위해 사용
* **Test 세트:** 최종 선택된 시스템의 성능을 편향 없이(Unbiased) 평가하기 위해 사용
* 필수가 아닌 경우: 편향 없는 최종 성적표가 굳이 필요 없고 빠르게 시제품을 개발하는 목적이라면 Test 세트 없이 Train/Dev 세트만으로 진행하기도 합니다.

## 6. 평가 지표 및 검증/테스트 세트의 변경 시점 (When to Change Metrics & Sets)

개발 도중 **목표 설정(평가 지표)이 실제 비즈니스 목표와 맞지 않는다는 것을 깨달았다면 즉시 평가 지표나 데이터셋을 변경해야 합니다.**

### 예시: 고양이 이미지 분류 서비스

* **알고리즘 A:** 오차율 3% (하지만 유해/포르노 이미지를 고양이로 분류하여 사용자에게 노출됨)
* **알고리즘 B:** 오차율 5% (유해 이미지를 절대 노출하지 않음)
* 단순 분류 오차율(Classification Error)만 사용하면 알고리즘 A가 선택되지만, 서비스 관점에서는 알고리즘 B가 훨씬 우수합니다.

### 해결책: 가중치 손실 함수(Weighted Cost Function) 도입

유해 이미지($x^{(i)}$가 포르노인 경우)에 엄청난 가중치(예: $w^{(i)} = 100$)를 부여하여 손실 지표를 재정의합니다.

$$\text{Error} = \frac{1}{\sum w^{(i)}} \sum_{i=1}^{w} w^{(i)} \mathbb{I}\left(y^{(i)} \neq \hat{y}^{(i)}\right)$$

### 문제 해결의 2단계 분리 (Two-step Process)

1. **1단계 (목표 설정):** 올바른 과녁(Metric & Dev/Test Set)을 정의합니다.
2. **2단계 (목표 조준):** 정해진 과녁을 향해 화살을 쏘는 최적화(Cost function 감소, 모델 튜닝) 작업을 진행합니다.
